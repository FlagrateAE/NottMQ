# Опис проекту

**NottMQ** — це асинхронний брокер повідомлень для Інтернету речей (IoT), побудований за патерном Publish/Subscribe. Мета проєкту - розробка надійного алгоритмічного ядра з нуля без використання сторонніх MQTT-бібліотек для парсингу протоколу чи управління мережею. Проєкт фокусується на строгій відповідності офіційному стандарту протоколу, безпечній обробці мережевих потоків та всебічній доказовій верифікації якості коду через сучасні інженерні практики тестування (PBT, диференційне, мутаційне та апаратне тестування).

Ключові компоненти системи:
* Власний бінарний кодек для серіалізації/десеріалізації пакетів MQTT v3.1.1.
* Структура даних **Topic Trie** (префіксне дерево) для швидкої та коректної маршрутизації повідомлень за топіками з підтримкою wildcards (`+`, `#`).
* Мережевий шар на базі **System.IO.Pipelines** для ефективного неблокуючого читання TCP-потоків.
* Стейт-машина для управління клієнтськими сесіями та чергами гарантованої доставки (QoS 0 та QoS 1).

# Специфікація та scope

Фундаментом проєкту є дотримання [офіційного стандарту OASIS MQTT v3.1.1](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html). Стандарт містить чітко нумеровані вимоги (конформанси, наприклад, `[MQTT-3.1.2-1]`), що дозволяє транслювати їх безпосередньо у тести.

### Межі проєкту:
* **Підтримувані пакети:** `CONNECT`, `CONNACK`, `PUBLISH`, `PUBACK`, `SUBSCRIBE`, `SUBACK`, `UNSUBSCRIBE`, `UNSUBACK`, `PINGREQ`, `PINGRESP`, `DISCONNECT`.
* **Рівні гарантії доставки:**
  * **QoS 0 (At most once):** доставка за принципом Fire-and-Forget без збереження стану.
  * **QoS 1 (At least once):** гарантована доставка з квитуванням через `PUBACK` та повторною відправкою непідтверджених пакетів.
* **Клієнтські сесії:** базова підтримка `CleanSession = 1` (transient sessions в пам'яті).
* **Свідомо винесено за межі (out of scope / майбутні цілі):**
  * QoS 2 (`PUBREC`, `PUBREL`, `PUBCOMP`)
  * Збережені повідомлення (Retained Messages) та повідомлення заповіту (LWT — Last Will and Testament).
  * Персистентне збереження стану сесій (`CleanSession = 0`) на диск.

# Roadmap

1. **Бінарний парсер (`NottMQ.Protocol`):** моделі пакетів та кодеки для Fixed Header, Variable Header і Payload. Реалізація специфічного 7-бітного алгоритму кодування довжини "Remaining Length".  
   *Тестування: юніт-тести граничних значень + Property-Based Testing (FsCheck) для перевірки інваріантності Encode/Decode та стійкості до фрагментації потоку.*
2. **Мережевий шар та сесії (`NottMQ.Server`, `NottMQ.Core`):** асинхронний TCP-сервер на базі `System.IO.Pipelines` для коректного framing'у повідомлень без блокування потоків виконання. Обробка пакета `CONNECT`, видача валідного `CONNACK`, відстеження `KeepAlive` та обробка коректного закриття з'єднання `DISCONNECT`.  
   *Тестування: інтеграційні тести життєвого циклу підключення та Fuzz-тести на обрив з'єднання.*
3. **Маршрутизація (`NottMQ.Core`):** побудова структури даних Topic Trie з алгоритмами підписки, відписки та пошуку з підтримкою wildcards (`+`, `#`). Коректне очищення та обрізання порожніх вузлів (node pruning) під час `UNSUBSCRIBE`.  
   *Тестування: 100+ потокові стрес-тести конкурентності та диференційне тестування проти послідовного оракула для виявлення race conditions.*
4. **Стейт-машина та QoS (`NottMQ.Core`):** реалізація логіки обробки `PUBLISH`, `SUBSCRIBE`, `UNSUBSCRIBE`, серцебиття `PINGREQ`/`PINGRESP`. Забезпечення доставки QoS 0 та QoS 1 (з чергами очікування `PUBACK` та пересиланням).  
   *Тестування: Black-box E2E тестування за допомогою клієнта MQTTnet з перевіркою контрактів OASIS v3.1.1.*
5. **Комплексна верифікація та hardware-інтеграція:** проведення Fuzz-тестів TCP-шару, оцінка якості тестового набору через Stryker.NET (Mutation Testing), запуск фізичних E2E тестів з платами ESP32.

# Стек технологій

* **C#: .NET 10**
* **Файл рішення:** `NottMQ.sln` (єдина точка входу для збірки `dotnet build` та виконання тестів `dotnet test`)
* **Мережевий I/O:** `System.IO.Pipelines` (для ефективної роботи з неперервними байтовими TCP-потоками та зручного framing'у пакетів)
* **Юніт та інтеграційне тестування:** `xUnit` + `FluentAssertions`
* **Property-Based Testing (PBT):** `FsCheck` (генерація сотень комбінацій пакетів та послідовностей байтів із кастомними генераторами, що відповідають синтаксису MQTT)
* **Mutation Testing:** `Stryker.NET` (CLI-інструмент інжекції штучних мутацій у код `NottMQ.Protocol` та `NottMQ.Core` для перевірки здатності тестів виявляти логічні помилки)
* **Покриття коду:** `Coverlet` (зняття метрик Line та Branch coverage)
* **Тестовий клієнт для E2E:** `MQTTnet` (використовується виключно в тестах для симуляції зовнішнього еталонного клієнта)
* **Апаратне тестування:** **C** (для скетчів мікроконтролерів ESP32)

# Стратегія тестування

## 1. Property-Based Testing (рівень модулів)

PBT застосовується до алгоритмічної основи — бінарного кодека пакетів (`NottMQ.Protocol`). Замість обмеженої кількості ручних тест-кейсів, `FsCheck` генерує сотні випадкових варіантів даних для перевірки фундаментальних математичних інваріантів.

Оскільки стандарт MQTT забороняє певні символи (наприклад, нуль-байт `\0` або знаки wildcards `+`/`#` в справжніх назвах тем публікації `[MQTT-4.7.1-1]`), для тестів реєструються кастомні генератори `Arbitrary<PublishPacket>`:

```csharp
[Property(Arbitrary = new[] { typeof(MqttPacketGenerators) })]
public Property Encode_Decode_Roundtrip_Invariant_Holds(PublishPacket originalPacket)
{
    // Act: кодуємо пакет у байти та декодуємо назад
    var buffer = new ArrayBufferWriter<byte>();
    MqttEncoder.EncodePublish(originalPacket, buffer);
    
    var sequence = new ReadOnlySequence<byte>(buffer.WrittenMemory);
    var result = MqttDecoder.TryDecode(ref sequence, out var decodedPacket);

    // Assert: Декодований пакет має бути повністю еквівалентним оригіналу
    var isEquivalent = result &&
        decodedPacket is PublishPacket p &&
        p.PacketId == originalPacket.PacketId &&
        p.Topic == originalPacket.Topic &&
        p.QualityOfService == originalPacket.QualityOfService &&
        p.Retain == originalPacket.Retain &&
        p.Duplicate == originalPacket.Duplicate &&
        p.Payload.Span.SequenceEqual(originalPacket.Payload.Span);

    return isEquivalent.ToProperty();
}
```

Також PBT перевіряє **інваріант стійкості до фрагментації TCP**: валідний закодований пакет розрізається на довільні шматки випадкового розміру (від 1 байта до всього масиву), які порційно згодовуються в пайплайн декодера; кінцевий результат декодування зобов'язаний бути ідентичним цілісному пакету.

## 2. End-to-End тестування на базі специфікації OASIS

E2E тести перевіряють поводження системи як чорної скриньки (black-box). Брокер піднімається на випадковому вільному порту (`port: 0`), а сторонній еталонний клієнт `MQTTnet` виконує сценарії взаємодії. Назви тестів безпосередньо мапляться на пункти специфікації OASIS:

```csharp
[Fact]
public async Task Test_MQTT_3_8_4_1_Server_Must_Respond_With_Suback()
{
    // Arrange: локальний запуск NottMQ брокера на випадковому вільному порті
    await using var broker = new NottMQBroker(port: 0);
    await broker.StartAsync();

    var client = new MqttFactory().CreateMqttClient();
    var options = new MqttClientOptionsBuilder()
        .WithTcpServer("127.0.0.1", broker.Port)
        .Build();

    await client.ConnectAsync(options);

    // Act: надсилаємо запит на підписку
    var result = await client.SubscribeAsync("sensor/temperature", MqttQualityOfServiceLevel.AtLeastOnce);

    // Assert: OASIS [MQTT-3.8.4-1] вимагає відповіді пакетом SUBACK з кодом дозволеного QoS
    result.Items.Should().ContainSingle();
    result.Items.First().ResultCode.Should().Be(MqttClientSubscribeResultCode.GrantedQoS1);
}
```

## 3. Concurrency та стрес-тестування з оракулом

Модуль маршрутизації **Topic Trie** є критичною зоною для race conditions та блокувань під час одночасного читання (`PUBLISH`) та модифікації дерева (`SUBSCRIBE`, `UNSUBSCRIBE`).

У `NottMQ.Tests.Stress` реалізується комбінований підхід:
1. **Стрес-навантаження:** 100+ конкурентних асинхронних задач одночасно виконують підписку, публікацію та видалення підписок (включно зі складними багаторівневими wildcards `sport/tennis/#` та `+/tennis/+`). Перевіряється відсутність `NullReferenceException`, дедлоків та збоїв пам'яті.
2. **Диференційне тестування з оракулом:** паралельно з висококонкурентним деревом розробляється простий, детермінований оракул на базі звичайних списків під блокуванням `lock`. Кожна операція дублюється в обидва сховища, і після серії паралельних дій списки одержувачів для кожного з топіків звіряються з оракулом. Будь-яка розбіжність вказує на порушення операцій чи помилки при обрізанні вузлів дерева (node pruning) при відписці.

## 4. Fuzz-тестування мережевого шару

Для перевірки відмовостійкості TCP-пайплайна виконується подача аномального трафіку на відкритий сокет брокера:
* Випадкові байтові послідовності замість заголовків MQTT.
* Невідповідні протоколи (наприклад, відправка HTTP GET запитів у порт брокера).
* Пакети з аномальним значенням `Remaining Length` (наприклад, оголошено розмір 256 МБ, а з'єднання закривається після 2 байтів).
* **Критерій стійкості:** коректне закриття сокета з боку брокера без витоку ресурсів чи аварійного падіння процесу (`OutOfMemoryException`, `IndexOutOfRangeException`). Після завершення сесії fuzz-тестування брокер перевіряється стандартним health-check пінгом (`PINGREQ`/`PINGRESP`), щоб підтвердити збереження повної працездатності.

## 5. Мутаційне тестування

Для верифікації якості тестового покриття застосовується інструмент **Stryker.NET**.
* **Цільові проєкти:** `NottMQ.Protocol` та `NottMQ.Core` (алгоритмічний код, що містить логічні розгалуження, бітові операції та роботу зі структурами даних).
* **Тестова база:** `NottMQ.Tests.Unit`. Щоб уникнути багатогодинних прогонів, тривалі стрес-тести винесені в окремий проєкт і не запускаються Stryker'ом.
* **Критерій успіху:** цільовий показник **Mutation Score $\ge$ 75-80%** (відсоток штучно інжектованих багів, які призвели до падіння юніт-тестів).

## 6. Code coverage

Збір метрик покриття коду здійснюється через **Coverlet** під час виконання `dotnet test`:
* Вимірюються параметри: **Line coverage** та **Branch coverage**.
* Цільовий показник покриття для бізнес-логіки та протокольного коду становить **$\ge$ 80%**.

## 7. Апаратне E2E тестування на базі ESP32

Фінальний етап підтверджує функціональність системи в реальному IoT-середовищі з реальними обмеженнями апаратних плат:
* **ESP32 Publisher:** плата підключається по Wi-Fi до IP-адреси NottMQ брокера та надсилає повідомлення `PUBLISH` у топік керування за допомогою бібліотеки `PubSubClient`. Payload - стан світлодіода: 3 байти - R, G, B.
* **ESP32 Subscriber (зі світлодіодом):** плата оформлює підписку `SUBSCRIBE` на відповідний топік. При отриманні маршрутизованого брокером повідомлення, змінює стан світлодіода.
* Тест доводить життєздатність брокера при взаємодії з реальними вбудованими клієнтами з обмеженими ресурсами.
